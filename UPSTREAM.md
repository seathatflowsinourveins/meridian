# Upstream register

Every tool this repo installs or integrates has a row here: what it is, the exact version or
commit, the page it was read from, the date it was read, and what it is used for.
"upstream" means the thing is used as its maintainers ship it. "own design" means it was written
here and no upstream ships it.

A row is added in the same commit that adds the tool. Versions are taken from the running distro
or the lockfile, not from memory. Transitive Python packages are pinned with hashes in `uv.lock`.

## Agent runtimes (`deploy/wsl/setup.sh agents`)

By the owner's decision of 2026-11-12 the agent runtimes update themselves where the tool can,
and each was installed at its newest release. They update in sessions the owner starts: launches
in which Orca types the prompt set `DISABLE_AUTOUPDATER=1` (Claude Code),
`AGY_CLI_DISABLE_AUTO_UPDATE=true` (Antigravity) and `check_for_update_on_startup=false`
(Codex), and Orca's terminals run Codex with `--no-daemon` (strings in the Orca 1.4.257 server
bundle). The 7-day wait for new releases applies to the Python dependencies only
(`pyproject.toml`). A pin here is the release a rebuilt distro starts from: the runtime's own
download is checked against the publisher's checksum or the registry's integrity value before
it runs, while an npm package's dependencies resolve from the registry on the day of the
install, and the Codex plugin follows its default branch from a recorded first commit.
`setup.sh agents-check` accepts the pinned version or newer. Sign-ins are the owner's.

Notes on the agent runtimes:

- **Orca's defaults are kept.** Agents start in bypass mode (`--dangerously-skip-permissions`,
  `--dangerously-bypass-approvals-and-sandbox`), Orca writes its status hooks into each agent's
  own configuration and pre-trusts each worktree. `orca-ide agent hooks off` removes the hooks.
- **Loopback only.** With mirrored networking a listener on every interface is reachable from
  the network, so the server binds 127.0.0.1 and refuses public addresses, and `agents-check`
  fails if any TCP or UDP socket of the service, of its terminal daemon's scope or of its
  terminals' slices (so of any agent) listens elsewhere. The Windows app reaches it at
  `ws://127.0.0.1:6790`. A server started without `--bind 127.0.0.1` (`orca-ide serve`,
  `serve service install`) can listen on every interface, so agents only ever start the
  service. `orca-ide pair` would first open the server to the network (the service refuses), so
  the owner pairs once with `setup.sh orca-pair`, a foreground run on loopback with the
  service's environment. A headless pairing link does not expire and grants shell access as
  the owner: it is printed to the owner's terminal only, never logged or committed, and
  `orca-pair` refuses to run in a terminal Orca started, whose output other Orca sessions can
  read (`orca-ide terminal read`).
- **Orca and sign-ins.** Orca's docs say it reads the existing Claude Code login to ask
  Anthropic for usage figures when a window is focused. That is Orca's own feature, not set up
  here; whether to keep it is the owner's decision.
- **No account-linked tools, no MCP.** claude.ai connectors and synced plugins (Claude Code)
  and ChatGPT apps (Codex) are off, so no account connector, a broker one included, reaches an
  agent here. MCP is off machine-wide for Claude Code and Codex. Antigravity has no such
  switch: `agents-check` looks for its MCP, plugin and hook files, and
  `tests/test_agent_config.py` keeps agent configuration out of the repository.
- **Codex's system skills stay.** Codex 0.167.2 ships five skills in `~/.codex/skills/.system`
  (imagegen, openai-docs, review-agent, skill-creator, skill-installer); no setting to switch
  them off was found. `skill-installer` fetches a skill from GitHub only when asked, and no MCP
  server a skill asks for is installed.
- **Subscription sign-ins stay in their own tools.** `dsh-tui` offers to sign in with ChatGPT,
  Claude or Grok subscriptions; that is not used here (Anthropic's terms forbid third-party
  tools routing requests through plan credentials). DeepSeek Harness uses a DeepSeek API key.
- **Antigravity's terms** call third-party software that accesses the service a breach, and its
  FAQ says wrapping `agy` inside third-party applications is not supported on consumer plans.
  Orca runs the official binary in its terminal and reads its usage; whether that is acceptable
  is the owner's decision.

Notes on the order budget, measured by the soak (`evidence/M2-order-budget-*-soak.json`):

- **It holds the request past the budget; it never refuses it for being over the budget.** A
  request waits in the pacer's queue until the bucket has a token, most urgent kind first, and
  neither the queue nor the wait has a limit. An entry also waits until the bucket holds more
  tokens than its protection reserve. A queued request leaves the queue unsent in four ways:
  its caller's admission check turns false (the caller withdrew it; in the soak, an entry not
  sent within 30 s); it is an entry whose reserve would reach the burst (`refuse(reason)` is
  called, and `request()` raises `PacerRefused` if that is already so when it is made); it is
  an entry whose reserve cannot be worked out (reserve rows missing, or a position count that is
  not a whole number), which is dropped silently, so a caller checks reserve authority in its own
  admission, as Sextant's Alpaca gateway does; or, fourth, in the send itself: the pacer
  spends the token and takes the request off the queue before it calls `send`, so a `send` that
  returns or raises without calling its wire hook, or whose hook raises `ValueError` because
  admission is false by then, sends nothing. An exception raised inside `send` (that
  `ValueError` among them) comes out of whichever `request()` or `drain()` call started that
  drain, and that call may have been made for another request, which may already be sent or
  still be queued: a raise from `request()` is not always about the request just made. A hook
  kept and called after `send` returned raises `ValueError` at that later call, not out of
  `request()` or `drain()`. This is the owner's design (Sextant ADR-0009, R6),
  kept as it is because the Alpaca adapter of M3 relies on it. Whether "refused" may mean "held
  until the window has room, or withdrawn by its caller" is the owner's to confirm.
- **The cap is 179, not 180.** The refill interval rounds up (370,370,371 ns for 162 refills a
  minute), so the 162nd refill lands 102 ns after the window: a full burst of 18 plus 161
  refills. That holds for any budget and burst: the cap is always one under the budget.
  Rounding down instead, `(window_ns - 1) // (limit - burst)`, would give exactly the budget
  for a window as long as this one (a very short window would need a guard against going over);
  that is a change to the owner's arithmetic and is not made here.
  After a quiet spell the bucket is full again, and the window that follows holds 179 too.
  Under steady demand above the budget it sends 161 to 163 a minute, because the burst is
  shared with the budget rather than added to it.
- **The budget holds within one pacer, not across a restart.** A new `AccountPacer` starts with
  a full burst and no memory of the last 60 s; `to_state()` and `restore()` carry only the wire
  counters, not the tokens or a 429 pause. Sextant's Alpaca adapter builds a new pacer each time
  the node connects, so a start within 60 s of the previous run's last request can add up to one
  burst (18) to that window. Each start adds a burst: with requests always waiting, one pacer
  sends 179 in its first 60 s, a restart at 30 s makes that 196 (a burst and 80 refills, twice),
  and restarts at 20 s and 40 s make it 213 (a burst and 53 refills, three times), past
  Alpaca's 200. These counts come from running the pacer alone with the fixture rows; the soak
  does not restart it. The M3 lane has to start a pacer empty, or wait out the window.

## Notes on choices

- **Node 24 rather than 26.** Both are LTS lines with a release on 2026-11-10. v24 is the older
  line, picked so the agent CLIs are less likely to meet an unsupported runtime. This is a judgement, not an upstream recommendation. v26.13.1 would be
  sha256 `5c063e46bab0fbc1c17cc445d7ff129cbdcd0471be6ed83b6ab864f8143bc864`.
- **uv 0.13.7 rather than 0.13.8.** 0.13.8 was published on 2026-11-12, the day of this sitting.
  The project applies a 7-day cooldown to new releases, so the tool that enforces it is held to
  the same rule.
- **`gh` from GitHub's release, not the Ubuntu archive.** Ubuntu's package (2.46.0-4) is far
  behind and inside two high advisories, one of which sends the signed-in token to third-party
  mirrors, and agents here run without prompts. GitHub's release tarball is pinned and
  checksum-checked like the other tools; GitHub's apt repository would work too, but adds a
  root-level package source.
- **The engine is a release candidate.** Upstream says release candidates are for testing and
  not for real capital. That fits a paper-only harness; it also means the API can change between
  candidates, so the pin is exact.
- **The adapter does not check the account.** NautilusTrader 2.0.0rc9's Interactive Brokers
  adapter takes the configured account id on trust and never reads the Gateway's account list.
  That is why `meridian/ib_probe.py` and `meridian/boundary.py` exist and run first.
- **Upstream's order-placing examples were read and not used as they are.** `exec_tester.py`
  opens a futures position on start. The built-in `ExecTester` strategy does not cancel on
  acceptance, so its order reaches a terminal state only at stop, and it submits again if the
  order is rejected or cancelled during the run. `IbV2OrderStrategy` submits once and cancels
  on acceptance, which is what M1 needs.
- **A fill is a failure in order mode.** The adapter refuses reduce-only orders, so upstream's
  close-on-stop cannot close a position. The lane switches close-on-stop off and reports a fill
  in order mode as a failed run.
- **Fill mode closes the way upstream's `SpreadOrderStrategy` does.** That example, in the same
  vendored file, answers a fill with one opposite order of the filled quantity
  (`event.last_qty`). Fill mode does the same, with DAY LIMIT orders priced 2% past the quote
  instead of market orders, so neither order can fill at an unbounded price, and it places at
  most these two orders. The quote is delayed data: the BUY is priced from it (crossed quotes
  are skipped), the SELL from the lower of the delayed bid and the BUY's live fill price. A move
  of more than 2% can still leave an order working at stop; the run then fails and says so
  rather than chase the price. The engine's `cache.orders_inflight` (read in the installed
  2.0.0rc9 stubs) is counted at stop as well as open orders.
- **The account check runs twice.** The adapter opens its own connections after the check, so
  the lane asks the Gateway again after the run and writes no evidence if the answer changed.
  It does not hold a connection open during the run.
- **Dependabot and uv.** `required-version` is not set in `pyproject.toml`, because Dependabot
  brings its own uv. uv is pinned where it is installed instead.
- **Upstream example files are LGPL-3.0.** They are kept verbatim with their headers, next to
  NautilusTrader's licence file, the GPL-3.0 text and a notice. No licence has been chosen for
  this repository's own code; that is the owner's decision.
- **This instance was brought to the definition by hand.** The running `meridian` distro was
  installed from an earlier version of `deploy/wsl/meridian.user-data`. Each later change to the
  definition was applied to it by hand on 2026-11-12: New York time, the machine-wide connector
  setting, the Gateway libraries, Ubuntu Insights consent and timers, the `paper` user's home
  entry, undoing the uv installer's shell edits (backed up under `~/.cache/meridian/`), and
  switching off `wsl-pro.service`. The definition itself was proven from scratch the same
  evening: a throwaway distro installed from commit `5d51c9c` finished cloud-init without
  errors, passed every line of `setup.sh check`, came up with systemd `running` and only 5
  upgrades left, and was then unregistered. The `wsl-pro.service` line came after that proof:
  it has been through cloud-init's schema check and this instance, not a fresh install.
  `package_upgrade` has not been applied to the running instance: 133 package upgrades wait
  until the Gateway session can be interrupted, and Ubuntu's unattended security upgrades stay
  on as the image ships them.
