# ADR 0001: semble for code search (plan 8.7, retrieval slot 2)

**Status: not adopted.** Decided 2026-11-12 by measurement at `f65d835` (`main` at the time). The [questions](data/0001-questions.json), the [plans](data/0001-plans.json) and the decision rule were committed in `78dedd5` before either method ran; [harness](data/0001_measure.py), [results](data/0001-results.json). Added on 2026-11-13, after a check across the ADRs and with the results unchanged: the ripgrep-alone row, the [always-on counts](data/0001-always-on.json) and their [counter](data/0001_count_tokens.py).

## Need

Agents here find code with ripgrep (Claude Code 2.1.322 bundles ripgrep 14.1.1 as its Grep tool). pyright 1.1.414, the repo's own dev dependency, is used here as the command-line checker (`uv run pyright`), not for navigation: no agent runtime here is known to give its agents a language-server client. Claude Code keeps its LSP tool inactive until a code intelligence plugin is installed ([tools reference](https://code.claude.com/docs/en/tools-reference.md#lsp-tool-behavior), read 2026-11-13), and `claude plugin list` shows only `codex@openai-codex`; `codex features list` (Codex 0.167.2) and dsh 0.2.2-rc.1's help and default profile configuration name none; Antigravity was not checked. Slot 1 is the baseline plan 8.7 names, "plain search plus pyright": ripgrep plus at most one pyright definition or references lookup. Those lookups were made by this ADR's own harness through pyright's language server, not by an agent, so the results give ripgrep alone as well. Slot 2 is semantic code search, kept only if it beats slot 1 on a fixed question set by a margin set in advance. Prior evidence, as plan 8.7 states it (the plan names no source and it was not checked here; it is about memory systems, not code search): a 2026 benchmark found 11 of 12 memory-system pairings did not beat a memory-off baseline for coding agents.

## Candidate

[MinishLab/semble](https://github.com/MinishLab/semble) **0.7.2**: tag commit `bb746c9`, on PyPI 2026-11-03 (0.7.3, of 2026-11-08, is inside the 7-day wait). MIT. Maintainers Thomas van Dongen and Stéphan Tulkens (MinishLab). Read 2026-11-12. It ranks tree-sitter chunks by BM25 plus static embeddings from [`minishlab/potion-code-16M-v2`](https://huggingface.co/minishlab/potion-code-16M-v2) (MIT, revision `e9d2a44`), on CPU.

## Advisories (GitHub, 2026-11-12)

None for semble, in its repository or in the global database. None for any of the 52 packages at the versions resolved with the 7-day cutoff: 32 for the CLI, plus 20 for the `mcp` extra, which resolves to `mcp` 2.3.0, above the four October advisories against `mcp` below 2.2.0. Queried as `affects=<name>@<version>`; known-vulnerable control versions did return advisories. semble publishes no security policy.

## What it installs, writes and sends

Read in the 0.7.2 source and its dependencies; checked with an audit hook (Python-level network calls, process starts, files opened for writing) in the model download and in all 186 `semble search` calls the harness made (6 for the index builds, 180 for the questions). `semble --version`, the in-process timing and the MCP-definition step were not logged, and hf_xet's own connections are known only from its log.
- One CLI with 32 packages (115 MB) in its own environment; no hooks. Here (24 files to index, a local path) `semble search` started no process; with 200 or more files to chunk it uses 4 worker processes (`SEMBLE_INDEX_WORKERS=0` turns them off). `semble` with no subcommand is an MCP server on stdio, which needs the `mcp` extra (52 packages in all); `--http` serves on 127.0.0.1:8000. Given a git URL (https, http, ssh, git, git+ssh, file, or the scp form), the CLI runs `git clone` on it with the user's git configuration and credentials (the MCP server accepts only http and https).
- First use only: the model, 33.5 MB (33.6 MB with the rest of `$HF_HOME`), from huggingface.co, which is also sent any stored Hugging Face token (`HF_HUB_DISABLE_IMPLICIT_TOKEN=1` stops that); its large file comes through hf_xet from `cas-server.xethub.hf.co` and `us.aws.cdn.hf.co`. On its first Hub request huggingface_hub 2.4.0 also fetches `/api/agent-harnesses`, a list of agent variables that Hugging Face keeps and can change (on 2026-11-12 it named `CLAUDECODE`, `CODEX_THREAD_ID`, `DSH_SHELL` and others), caches it for 24 hours in `$HF_HOME/.agent_harnesses.json`, and adds `agent/<name>` to its User-Agent when one matches; `HF_HUB_DISABLE_TELEMETRY=1` stops both for semble. The 186 later `semble search` calls made no network call.
- Writes: the model, `.agent_harnesses.json` and hf_xet's log and cache folder (`xet/`) under `$HF_HOME` (default `~/.cache/huggingface`); native grammar libraries, extracted from the package to `~/.cache/semble/grammars/` with a checksum check, and loaded from there later without one; for each indexed folder, `~/.cache/semble/<sha256 of its path>/index*/` (0.86 MB here), whose `chunks.json` is a second copy of the indexed text (0.26 MB; the 24 files are 0.21 MB); `savings.jsonl`, one line of counts per search. Outside those, only temporary files in `/tmp`, removed at once. In the first of the two earlier runs (see Results), and not in the committed one, the first two `semble search` calls also made CPython cache three standard-library modules as `.pyc` files (`encodings/cp437`, `importlib/readers`, `importlib/resources/_adapters`) in the uv-managed interpreter's own `__pycache__` folders, outside the throwaway environment; they are regenerable and were left in place.
- `semble install` (not run) pre-selects every coding agent it detects and defaults to yes. For Claude Code it would add `mcpServers.semble` = `uvx --from 'semble[mcp]==0.7.2' semble` (no env) to `~/.claude.json`, a block to `~/.claude/CLAUDE.md` and `~/.claude/agents/semble-search.md`. With that entry uvx resolves `semble[mcp]` from PyPI into uv's cache when the agent starts, outside the 7-day cutoff and without `HF_HUB_DISABLE_TELEMETRY`. On this machine the entry would start nothing: MCP servers are off machine-wide for Claude Code and Codex (`AGENTS.md`), by an empty `mcpServers` in `/etc/claude-code/managed-mcp.json`, which takes exclusive control of MCP, and an empty allowlist in `/etc/codex/requirements.toml`; `deploy/wsl/setup.sh agents-check` passes only while both are empty. The installer edits the files itself and starts no process, so it would still write all three.
- Indexed here with `--content all`: 24 of the 35 tracked files. Not indexed: `deploy/wsl/meridian.user-data`, `evidence/*.json`, `uv.lock`, the dotfiles and the licence texts.

## Always-on context

Without semble: nothing added. Grep is built into Claude Code, and pyright runs only as a command. The figures below are a reconstruction, not a measurement before and after in sessions: `semble install` was not run, and the texts its default install for Claude Code (MCP, instructions, sub-agent) would add were taken from semble 0.7.2 (its source and, for the tool definitions, the server object the harness built) and counted. With that install, where MCP is allowed, every session would load:
- 3,868 characters of MCP tool definitions (1,017 tokens) and 439 of server instructions (95);
- the 2,021-character CLAUDE.md block (480);
- the 236-character sub-agent description (44).

That is 6,564 characters, 1,636 tokens; on this machine the MCP part, 1,112 of them, would not load while MCP is off (above). The skill variant is 354 characters (78 tokens). Tokens are counted with o200k_base, OpenAI's vocabulary (sha256 `446a9538…1a2d`), as a proxy, because Claude's tokenizer is not available offline: they size the text and are not Claude's own counts. They were first counted outside the harness, with nothing committed about how, and counted again on 2026-11-13 with the published [counter](data/0001_count_tokens.py) (sha256 `a8dcf1e4…7502`; give it `--vocab-dir`), which gave the same figures; [0001-always-on.json](data/0001-always-on.json) lists each text's place in semble's source, its size and its sha256. The texts are semble's and are not published here. The 115 MB and Claude Code's version were measured outside the harness; the results file holds only the characters of the tool definitions and server instructions.

## Method (fixed in `78dedd5`)

30 questions an agent would ask here (10 where-is-this-check, 4 callers, 2 vendored upstream, 5 run record and engine run (Q19 to Q21 are the engine log, the order price and the probe deadline), 5 tests, 4 ops; Q08, the pass-or-fail rule, is filed under checks and Q13, a subclass lookup, under callers), each answered as file and symbol and checked by hand. A separate agent, given only the questions and AGENTS.md (no code, no tool use), wrote each method's moves. Its ripgrep searches use words from the question or AGENTS.md or a plain code spelling of a phrase in them (run record: `run_record`, `RunRecord`), and three names from outside those (Q09 `getenv`, Q10 `orders_open` and `positions_open`); no rank depends on those three. For slot 1: one to three ripgrep searches (with `--hidden`, as the Grep tool does) and at most one pyright definition or references lookup, which 5 of the 30 plans have (Q07 and Q11 to Q14) and which the harness makes with its own language-server client. For semble: one query and content type, top 5. The corpus is the frozen commit's 35 tracked files, checked blob by blob. A result counts when it is in the answer's file and its lines overlap the answer's span: for semble the chunk's lines, for slot 1 the lines its searches and lookup returned, not the unit span the results file lists. A question with several answers counts when any one is found. Slot 1's hit lines are grouped by their enclosing def, class or bash function, else Python top-level statement, else paragraph, and ranked by how many searches hit them, then by hit lines, then by first appearance in the searches' output (searches in plan order); the lookup goes first, and it asks for references with `includeDeclaration` false, which in pyright 1.1.414 also leaves out the reference at the position asked from. No real task was run. Plan 8.6 asks each ADR for "one real task done with and without it"; plan 8.7 says of this candidate that it is "measured against plain search plus pyright on a fixed set of questions about the repo", and does not say whether that set replaces the task. Only the question set was run. **Rule: adopt only if semble answers at least 5 more questions within the top 3, and no fewer within the top 1 and the top 5.**

## Results (30 questions; identical over 3 repeats; two earlier runs from empty caches, with the harness at `78dedd5` and `5ca07bd`, gave the same ranks and are not committed)

| | top 1 | top 3 | top 5 | median time per question | median text returned |
|---|---|---|---|---|---|
| **slot 1 as fixed before the run: ripgrep + the harness's pyright lookup** | **19** | **24** | **26** | 0.011 s (pyright ready once, 1.4 s) | 1,243 chars |
| **ripgrep alone (slot 1 without the lookup): what an agent here can run** | **20** | **25** | **26** | not timed apart | 1,243 chars |
| **semble, the plan's query** | **16** | **21** | **23** | 0.66 s per CLI call (0.9 ms in process) | 4,610 chars |
| slot 1, unranked printed order | 11 | 19 | 21 | | |
| semble, question verbatim, all content | 13 | 15 | 16 | | |

Within the top 3, semble did better on where-is-this-check (10 of 10 against 7, and 8 for ripgrep alone). It did worse on tests (1 of 5 against 4; 0 of 5 without Q25's helper, below), callers (3 of 4 against 4; ripgrep alone puts all 4 in the top 3, and on Q13 pyright's lookup returned only the import line), vendored upstream (0 of 2 against 1) and ops (2 of 4 against 3). It ties on the run-record group (5 of 5). Its ranking scales test and `examples/` files by 0.3, and it misses files it does not index. Index: 365 chunks, built in 0.10 s with the model loaded; the first CLI call takes 1.3 s, and the model download and load 3.3 s. Checked after the run, with the frozen files left as they are: Q25's key also accepts the helper `filled` (`tests/test_run_record.py:93-95`), which is not a test, and semble's only test hit within the top 3 (rank 2, chunk 81-98) rests on it; without it semble scores 16, 20 and 22. Q16's key, upstream's `ib_account_id`, shows the rule, but the lane never calls it (the raw id goes through `build_ib_live_node` to the compiled adapter, outside the corpus); both methods returned the refusal in `single_paper_form_account` first and scored nothing. Slot 1's one hit line on Q28, `ci.yml:20`, is inside the listed unit 11-39 but outside the gitleaks step 32-39; scored on unit spans, slot 1 would have 20, 25 and 27. Requiring both callers on Q11, Q12 and Q14 gives slot 1 16, 24 and 26 and semble 15, 20 and 22. The lookups moved Q07 from 1st to 4th and Q13 from 1st to 2nd (each was asked from the answer's own line) and Q12 from 2nd to 1st; without them slot 1 scores 20, 25 and 26, the table's ripgrep-alone row. That row was computed on 2026-11-13 with the committed harness, offline, from the same searches on the frozen files, after all 30 recorded slot 1 results had come out the same; in ripgrep's printed order, ripgrep alone scores 10, 20 and 22. None of these changes the decision.

## Decision

Not adopted. The rule compares semble with slot 1 as fixed before the run: within the top 3 semble answers 21 questions against 24, 3 fewer where 5 more were required, and within the top 1 and the top 5 it answers 16 against 19 and 23 against 26, 3 fewer each where no fewer were required (without Q25's helper: 3, 4 and 4 fewer at top 1, 3 and 5). Against ripgrep alone (20, 25 and 26) it answers 4, 4 and 3 fewer (4, 5 and 4 without the helper), so the rule fails on all three counts whichever baseline is taken. Even against slot 1 in ripgrep's printed order (pyright's lookup still first) its lead at top 3 is 2 (1 without the helper), and against ripgrep alone in that order it is 1 (0). As a CLI it would cost about 60 times slot 1's time per question and 3.7 times its printed text; with the default install (MCP), which this machine's policy does not allow as it stands, it would cost about 1,600 tokens in every session, with searches at 0.9 ms in process. Either way it keeps a second copy of the code in `~/.cache`. Slot 3 (a context store) is therefore measured against slot 1. Look at semble again only if a question set on a larger repo shows slot 1 failing.
