# ADR 0007: openai/plugins, the official Codex plugins (plan 8.6)

**Status: not adopted.** Decided 2026-11-13. This ADR covers 2 additions from one source, as plan 8.6's candidate list names it (`openai/plugins`), and decides each separately: codex-security, on the source at the pin, a policy probe with the plugin itself and three runs of a real task without it (the arm with it could not be built here, so there is no with/without comparison); and the catalogue's superpowers 6.3.0, for which no with/without task was run. Assessed 2026-11-12; an independent re-check on 2026-11-13 ran 51 checks (44 confirmed, 6 corrected, 1 refuted) and agreed with the verdict; later checks at the source revised four of them (C13, C21, C35, C43; `prereg.corrected_since` in the [results file](0007-results.json), where the figures below come from unless another file is linked).

## Need

Codex here runs with plugins, apps and MCP off. `openai/plugins` is the catalogue Codex offers through `/plugins`. Of its 62 plugin folders, `codex-security` (vulnerability review, owners `@openai/cyber-products`) is the only OpenAI-maintained one that matches a task here: R4, a security review of `meridian/boundary.py`. Two third-party review entries were not assessed, since each needs a new third-party service and account: `coderabbit` (an unpinned `curl ... | sh` install of its CLI, a sign-in, code sent for remote processing) and `qodo` (a remote entry with no ref, a sign-in at install). Other tools here that review code, none of them run on R4: Codex's `/review`, `codex review` and its system skill `review-agent`; `/codex:review` and `/codex:adversarial-review` (openai/codex-plugin-cc 1.0.6) and Claude Code's `/security-review` and `/code-review`. Codex's review entries and `/security-review` are scoped to a change, not to a file at a commit as R4 is.

## What it installs, writes and sends

Read in the tree at the pin and in Codex's source; the candidate's code never ran.
- The catalogue: 62 plugin folders, 46 with skills (531 `SKILL.md`), 31 with MCP servers (26 remote vendor endpoints, 5 local; one runs `npx -y xcodebuildmcp@latest`, unpinned), 34 with app connectors (`public-equity-investing` bundles an `alpaca` broker connector), one `hooks.json` (figma).
- Codex with `plugins = true`: with the ChatGPT remote catalogue inactive, every start runs `git ls-remote` on `main` and, when the head moved, fetches it into `$CODEX_HOME/.tmp/plugins` and reinstalls curated plugins (`core-plugins/src/startup_sync.rs` 27-38, 185-196; `manager.rs` 769-790); with a ChatGPT login and `remote_plugin` on (the default), catalogue and bundles come from the ChatGPT backend. Either way it follows upstream, not a pin. An install writes `$CODEX_HOME/plugins/cache/...`, `plugins/data/...` and a `[plugins."..."]` table in `config.toml`. One sync already happened here before the requirements file: a 103 MB checkout of `d420d13` in `~/.codex/.tmp/plugins` (regenerable).
- codex-security: 15 skills; a stdio MCP server passed 45 environment names (among them `OPENAI_API_KEY` and AWS credential variables); app connectors linear, github, atlassian. It brotli-decompresses bundles (to 1,831,445 and 374,869 bytes) and runs them with `Module._compile`. Its main server registers 47 MCP tools, 22 visible to the model ([count](0007_mcp_model_tools.py)). Deep Scan starts `codex exec` workers with approval "never" and no sandbox mode, so here they would inherit `danger-full-access`. With MCP blocked, its `security-scan` skill falls back to running the launcher through the shell.

## Method

- Fixed before the runs: the [pre-registration](0007-prereg.txt) (sha256 `6485f6ab7b941137b147c1a6f9e7c751cf57b9d833efedcc0e6fc97eb1d4feec`), the re-check's fact sheet, with R4's brief, grading, run order (a1 b1 b2 a2 a3 b3, 2 more per arm on a one-success gap or a 2-2 tie) and the rule. Its file time is 2026-11-13 01:45:30 ET; the first probe with the plugin ran at 01:57:25 and a1 at 02:00:43. These are file times on the owner's machine and cannot be proved from the repository.
- Rule (pre-registration): adopt only if the preconditions hold (the plugins pins lifted, a vendored pinned copy, the bundled advisories fixed or accepted) and D(with) >= 2/3 while D(without) <= 1/3, median false findings no higher, median total tokens <= 3x, always-on delta <= 1,500 tokens. The assessment's wording of 2026-11-12 21:38 ET (not published) had one more branch: if D(without) already holds in 2 of 3, adopt only with equal D and at least 25 % fewer tokens. No record says why the sheet dropped it. Both fail on the preconditions.
- Arms: a = Codex 0.167.2 in the owner's `~/.codex` with its sign-in; b = the same plus codex-security from a vendored copy of the pin in a local marketplace. Neutral run names; the [arm key](0007-key.txt) kept outside the run folders. M1: 3 runs of `codex exec ... 'Reply with exactly the word OK. ...'` in a fresh clone of `9c5daaa`; always-on = `turn.completed.usage.input_tokens`.
- Task R4 at `96e82e6`, the [brief](0007-r4-brief.txt) verbatim. D = the `[DEFAULT]`-inheritance defect reported; other findings real or false against `39cb68e`; total tokens; checkout unchanged. Graded by the measuring agent's judgement ([grading per finding](0007-r4-grading.txt)).
- Added at run time, before a1: the [setup and grading check](0007_validate_r4.py), a1's [harness](0007_r4_run.sh) and [per-run counts](0007_run_summary.py). Where the pre-registration says a worktree, each run used a `git init` repository holding only `96e82e6` and its ancestors, with a stand-in HOME (a seatbelt only: with approvals and the sandbox bypassed, absolute paths stayed reachable). After a1: the false-finding criterion (02:05 ET); the [Gateway guard](0007_gateway_guard.sh) (02:41); the [a2 and a3 harness](0007_r4_run2.sh), [command review](0007_cmd_review.py), [hit context](0007_hit_context.py) and [cleanup](0007_cleanup_run.sh) (04:04 to 04:07); the definition of passed (04:12, after all runs). The scripts are records of what ran, not rerun harnesses; the [policy probe's marketplace builder](0007_make_market.py) too.
- Before every run a guard checked that nothing listened on the paper Gateway's port and that no Gateway process ran. The first run's guard matched command lines and stopped this series falsely at 02:04 ET, before a2; a2 and a3 used the fixed guard.

## Results

- Arm b could not be built, shown with the plugin itself: `/etc/codex/requirements.toml` pins `plugins`, `apps`, `skill_mcp_dependency_install` and `memories` false and has an empty `[mcp_servers]` allowlist in every `CODEX_HOME` (`setup.sh` `check_codex_requirements` 490-506 at `9c5daaa`). In a throwaway home `codex --enable plugins features list` still shows plugins false, a copy named `openai-curated` is refused as reserved, and `codex plugin add codex-security@ab-0007-pinned` reports it "not found". So no M1 with it, no R4 run with it, no delta.
- R4, arm a, 3 runs (a1 02:00, a2 04:04, a3 04:07 ET): D in 3 of 3; false findings 0, 0, 0; other true findings 3, 3, 4. Total tokens 270,138, 310,805 and 248,010 (median 270,138); 140, 116 and 120 s; 7, 8 and 7 model requests; exit 0, checkout unchanged, no sub-agent. Voids: none (a void run is one whose result is not counted for its arm because a stated rule was broken; a void in the arm with the addition counts against it). D(without) = 3/3 fails the pre-registration's D(without) <= 1/3.
- Web: every run used Codex's built-in web search (3, 4 and 3 items). The opened pages were IBKR API documentation and, in a3, also Python's `configparser` documentation, which a3's report cites for the `[DEFAULT]` finding; the command review printed queries, not opened pages, and missed that page; a later check of every item's results found no GitHub page. `39cb68e`, whose message names the defect, was on the public `main` during all runs: the one-commit repository kept it out of local git only. The review of every command found reads and Python on in-memory fixtures only: nothing ran the lane or the probe, opened a socket, or named `~/Jts`, a secret path, the main checkout or `39cb68e`.
- Written into the owner's `~/.codex` (names and counts only): 4 `[projects."<clone>"]` `trust_level` tables in `config.toml` (M1's clone and a1 to a3's, all since deleted); 6 thread rows with account-linked fields in `state_5.sqlite` and 74 item rows in `thread_history_1.sqlite`; 6 rollouts in `sessions/`. The runs' home check compared names only and missed the first two.
- Cost: 877,811 Codex tokens (M1 48,858, R4 828,953); no other runtime, no GitHub API call. Raw outputs (2.7 MB, account fields) stay on the owner's machine, not in this repository.

## Decision

codex-security: not adopted, by the pre-registered rule and equally by the assessment's wording: the preconditions fail (the pins are in place; the bundled advisories are neither fixed nor accepted), and D(with), the token ratio and the always-on delta cannot be measured here. Also weighed, as facts: the route follows upstream's head or the ChatGPT backend with no pin; the copy carries upstream's `main` skills under a release number npm never published and a licence field (Proprietary) unlike upstream's (Apache-2.0); it has high-severity bundled advisories, compiles a compressed runtime at start and starts workers that inherit an unsandboxed mode; it would add an estimated 1,293 tokens to every session; the catalogue carries a broker connector. Measuring it would need the `plugins` pin lifted and only its stdio server allowlisted, `apps` kept off, `remote_plugin` off and `[marketplaces] restrict_to_allowed_sources` set so the git catalogue is refused (`with_window` in the results file; untested).

superpowers 6.3.0: not adopted. No with/without task was run for it; it was decided on the same pins, which block it, and the same unpinned route. Overlap, as fact: Codex's subagents and Orca's worktrees do part of what its parallel-agent and worktree skills do; its content is obra/superpowers, which ADR 0005 measured for Claude Code at v7.0.2. Nothing is installed or enabled.

## Commands

- Pinned install: none by the documented route (https://learn.chatgpt.com/docs/plugins, read 2026-11-13: `/plugins` inside `codex`, no pin), and `codex plugin marketplace add openai/plugins --ref <sha>` is refused (reserved name). An untested route, refused here under the machine policy: copy `plugins/codex-security` from `d420d13` into a local marketplace `ab-0007-pinned` ([builder](0007_make_market.py)), then `codex plugin marketplace add <dir>` and `codex plugin add codex-security@ab-0007-pinned`.
- Removal: `codex plugin remove codex-security@<marketplace>` (removes its cache folder and `config.toml` entry), `codex plugin marketplace remove <name>`; archive any owner data, then delete `$CODEX_HOME/plugins/data/codex-security-<marketplace>/`, `$CODEX_HOME/state/plugins/codex-security`, `$CODEX_HOME/.tmp/plugins*` and the vendored folder; restore `/etc/codex/requirements.toml` from `deploy/wsl/meridian.user-data` 68-77 and run `setup.sh agents-check`.
