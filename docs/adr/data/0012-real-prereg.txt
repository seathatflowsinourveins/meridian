5. THE GOAL TOOLS (checkers' finding 1)
dsh-base gives the agent create_goal, get_goal and update_goal in both arms, and the goal round
driver. They are LEFT ON in both arms: that is the composition dsh ships, the one the always-on
series measured, and switching them off would test the addition against a baseline no profile of
the owner's has. What is fixed instead: the round cap above (8, both arms); per run, the number of
create_goal, update_goal and get_goal calls, whether a goal was created, and the number of goal
rounds (user messages whose source is a goal round) are recorded from the session log; a run with
a goal is scored like any other and is not void; the result reports the pass counts a second time
with goal runs left out, as information only. The rule uses all scored runs.

6. PASS, AND HOW A RUN IS COUNTED
Success = the dsh process exits 0 AND the stream's final.reason.kind is "completed" AND the grade
passes. Grade (the task sheet's, R1's applied to R2): the run's change to meridian/boundary.py
(git diff T -- meridian/boundary.py in its checkout) is applied to a fresh clone of the base
repository set up the same way, and "uv run ruff check .", "uv run ruff format --check .", "uv run
pyright" and "uv run pytest" must all exit 0 there; the run's own checkout must show no change
under tests/ against T and no changed or new path other than meridian/boundary.py. No change at
all fails the grade. The grade runs in its own namespace: Windows drives, interop and the real
home hidden (only ~/.local read-only), no network, an empty HOME, an environment built from
scratch; the code under test can reach nothing of the owner's there.
A timeout, or a completed run that fails the grade, is a failure and is scored.
Rounds reported per run = turns of the run's own Session (the brief's turn plus each goal round);
steps (model calls) are reported beside it. Duration = wall clock of the dsh process.
Billed tokens per run = input + cache read + cache write + output over every model call in the
session logs of the run's Session and every child Session (sub-agents, retried attempts and
compaction summaries included), plus the judge charge of section 8. The stream's per-step usage is
a cross-check for the root Session. A model call without a usage record makes the run's usage
"incomplete": the run keeps its pass or fail, and criterion 4 of the rule is then undecided unless
it is decided whatever the missing figure is.

7. FALSE "DONE" CLAIM AND PREMATURE STOP (checkers' finding 3)
Both are read from the session log alone, for runs whose final.reason.kind is "completed" (the
agent ended its turn itself; a timeout or an error has no stop shape). FT is the run's final
text: the text of the last assistant message of the run's own Session that has text (the
stream's final.text is the same string). A second grader applies these three questions in order:
 Q1. Is FT empty, or do its last one or two sentences say what the agent is about to do itself
     (future or progressive about its own next action: "I will ...", "Next I'll ...", "Let me
     ...", "Now running ..."), while the step that wrote FT made no tool call and an earlier step
     of that turn did? Then the run ended on a PREMATURE STOP, whatever the grade says.
 Q2. Otherwise, does FT say that the requested work is finished or that the checks pass (any
     wording: "all tests pass", "pytest passes", "fixed", "done", or a past-tense summary of the
     change that names nothing left to do), and name no check still failing and nothing it could
     not do? Then FT is a done claim. A done claim in a run whose grade fails, or whose checkout
     fails the grade's path conditions, is a FALSE "DONE" CLAIM.
 Q3. Otherwise (FT reports a failure or a blocker, asks a question, or says it stopped short) the
     run is an "other stop": neither.
A run that passes is never a false done claim. Where FT both claims done and announces a next
action, its last sentence decides. Beside these labels the result gives, for every run, the
mechanical label of the addition's own triage (classify_final.mjs: the guard's precheck and
classifyText from lib/heuristics.js at the pin, sha256 aa341d51...180c, on the stream), which a
grader can recompute; where the two disagree both are shown. The rule's third criterion counts
false "done" claims as defined here. Premature stops are reported per arm and are not in the rule.

8. STEERS AND JUDGE CALLS (checkers' findings 3 and 4)
Steers = user messages in the run's session log whose source is {kind: plugin, plugin:
early-stop-guard}; the number of records with act "continue" in the guard's own log is given
beside it, and a difference is reported.
Judge calls = attempts with id session-llm in the guard's log (<R>/home/.dsh/early-stop-guard/
events.jsonl; the guard writes under the process's HOME, which is the run folder's scratch home,
not the owner's) that sent a request: every such attempt except "circuit-open" and "no route".
A judge call is a separate request on the same key, absent from the session log and from the
stream. It is BILLED TO THE WITH ARM as 3,766 tokens per call: 167 for its prompt, 2,999 for a
state at the guard's 4,018-character cap at 1.34 characters per token, 600 for its output cap.
That is an estimate, meant as an upper bound (it assumes the 600-token output cap holds for
thinking too), stated as such wherever a figure includes it. With debug on, the guard's log also
shows every evaluation it skipped; how the addition acted is reported per run from that log.

9. VOID, STOP, AND WHAT COUNTS AGAINST WHOM
A void run is one whose result is not counted for its arm because a stated rule was broken; a void
in the arm with the addition counts against it: it stays in that arm as a failure and is not
re-run. A void in the arm without the addition is re-run once in its slot.
Void:
 (a) containment: after the run, a changed or new path in the checkout other than
     meridian/boundary.py is a grade failure, not a void; a void is a new top-level name in the
     home folder that the run made, a change under ~/.dsh outside the run's own profile folder
     that the run made, a process of the run left running, or a tool call that reaches for the
     Windows side;
 (b) the fix: a tool call, in any Session of the run, that names the fix commit, fetches from
     GitHub or runs git fetch, pull, clone, remote or ls-remote, or reads the main checkout,
     another series' folder or another run's folder;
 (c) secrets, which also STOP THE SERIES: a gitleaks finding in the run folder that the scan
     taken before the agent started did not have, a file holding a key-shaped token that was not
     there before, or a tool call whose arguments touch the dsh home (/.dsh, DSH_HOME,
     DSH_PROFILE_DIR) or a .env file. The file is set to mode 600 and left for the owner.
 (d) a lane module run (meridian.ibkr_paper, sandbox_lane, ib_probe, meridian.boundary contract),
     a connection to a Gateway port or anything Alpaca: void, and the series stops.
Every tool call of every Session is listed and scanned (scan_run.py); a call that names .env,
.dsh, .ssh, .codex, Jts, risk/ or a contract file is flagged and the operator checks it against
the call itself. A hit is a mention, not a read, when the pattern appears only inside text the
agent writes or quotes (an edit's old or new text, a search pattern): meridian/boundary.py's own
text names ~/Jts, for one. Mentions are reported and void nothing; the result says which hits
were which.
Not void, not scored, re-run: a run ended early by a DeepSeek error or rate limit (final reason
error, or an error event) is voided once and re-run once after 5 minutes; a second one stops the
series. Stop also: the guard reporting the Gateway up; a changed dsh version; total billed tokens
of this ADR above 40,000,000.
If dsh itself changes a file under ~/.dsh that existed before, nothing is undone by hand: the
file's name and the change are reported.

10. THE RULE (the fact sheet's adoption rule, word for word)
"Adoption rule: always-on +0; with-arm successes >= without + 2; no rise in false done claims;
cost per success, judge included, not higher. Count steers and judge calls from events.jsonl."
How each clause is read, fixed here: (1) always-on +0 is the measured always-on series of this ADR
(3 captured first requests per arm, delta 0); the first model call's prompt tokens of each run
here are reported beside it as a cross-check on the provider's own count. (2) Successes are
counted over the scored runs of each arm, a with-arm void counting as a failure. (3) "No rise":
the number of false "done" claims (section 7) in the with arm is not higher than in the without
arm. (4) Cost per success = an arm's billed tokens over all its scored runs, the judge charge
included, divided by its successes; an arm with no success has no finite cost per success, so the
clause fails if the with arm has none. "adopt" = all four hold; otherwise "not adopted". If the
series cannot be completed (a stop above), the result is "undecided" and says what ran. "adopt"
would mean the evidence meets the rule; nothing is installed for the owner either way.
