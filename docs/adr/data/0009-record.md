# ADR 0009: dsh-codex-peer, Codex as a peer of DeepSeek Harness (plan 8.6)

**Status: not adopted, 2026-11-13.** Decided on real task R4, run with and without the plugin plus a Codex-only reference arm on 2026-11-13 (09:05 to 09:47 ET), by the rule fixed before those runs: three of its clauses fail (Results). Assessed 2026-11-12; an independent re-check on 2026-11-13 ran 50 checks (46 confirmed, 4 corrected, 0 refuted) and agreed; an audit re-graded all nine real runs, partly blind, and agreed with every grade. Data: the real series' [results](0009-real-results.json), [pre-registration](0009-real-prereg.txt) and [arm key](0009-real-key.txt); the earlier [results](0009-results.json) (candidate record, rule history, always-on probes) with the probes' [aggregates](0009-always-on.json) and [key](0009-key.txt); R4's [brief](0009-brief-R4.txt) and [rubric](0009-rubric-R4.txt) with their [hash record](0009-prereg.txt). Scripts are under Commands. Facts read from upstream source and advisories are cited here and in the re-check, not all in the data files.

## Need

The plugin lets a DeepSeek Harness (dsh) session call the signed-in Codex CLI for a consult, a review or an implementation, and keep a dsh/Codex work list with owners, budgets and evidence. What already does part of that job here: Claude Code's openai/codex-plugin-cc 1.0.6 gives `/codex:review`, and Codex 0.167.2 runs as its own Orca worker (both in `AGENTS.md` lines 66-69 on `main` `9c5daaa`) and ships `codex exec review`; neither is reachable from inside a dsh session. Orca's tasks and gates track agent work. Each runtime's `/goal` keeps one session working toward one end state, and the owner sets goals (`docs/HANDBOOK.md`, Goals, on `m2/handbook-size-budget`); it is not a work list an agent keeps. `AGENTS.md` gives DeepSeek Harness mechanical tasks only. DeepSeek's own `@deepseek-ai/dsh-subagent-codex` 0.2.2-rc.1 (one-shot, bundles `@openai/codex` 0.153.4) is not installed either.

## What it installs, writes and sends

- Every runtime file of the plugin at the pin was read before its first load. `package.json`: no dependencies, no install script; peers `@deepseek-ai/dsh` and `@deepseek-ai/schemastery`; one bundle row `codex-peer`. Imports only `node:` built-ins and schemastery; no network code. An install writes the profile's `package.json`, lockfile and `node_modules`.
- At every dsh start: creates `${DSH_HOME:-~/.dsh}/codex-peer/runs`, reads the Codex `config.toml` for a `CODEX_CLI_PATH` line (never `auth.json`), and registers five model tools (`codex_ask`, `codex_review`, `codex_status`, `codex_plan`, `codex_task`) and one in-process `tools/pre-execute` approval listener. No system-prompt text, skill, command, hook script, MCP or LSP server.
- `codex_ask`, `codex_review`, a `codex_plan` critique and `codex_task run` start the signed-in Codex CLI (`codex exec --json -o <run>/answer.md [--output-schema <f>] --skip-git-repo-check -C <cwd> -s <sandbox> [-m <model>] -`), read-only for ask, plan and review, workspace-write for implement and `codex_task run`, danger-full-access if the model asks. No approval flag, so the stack's Codex config applies (`approval_policy = "never"`); by default no `--disable hooks` and no `CODEX_HOME` (`lib/config.js` lines 114-116 and 68-70), so children run with the owner's Codex hooks and write the owner's `~/.codex`. Launched through dsh's subprocess service (which drops secret-named variables); its `codex_status` version probe starts Codex with dsh's whole environment. Hard cap 1,800,000 ms; background job after 600,000 ms.
- Writes `runs/<id>/` (prompt, Codex event stream, stderr, answer, argv, usage), `runs.ndjson` (with each Codex thread id), `threads.json` and one unlocked `tasks.json`; nothing is pruned; by default each run is mirrored into `<cwd>/.codex-peer/` (`workspaceDir: ''` switches it off). Sends nothing itself: the Codex child sends the prompt and what it reads to OpenAI under the signed-in account; up to 120,000 bytes of its answer return to DeepSeek.
- Gate: `codex_plan` always asks; `codex_ask` asks for implement or a write sandbox; `codex_review` never asks; `codex_task` is never inspected. Orca's unit sets `DSH_PERMISSION_MODE=danger-full-access` (`deploy/wsl/setup.sh` line 92 on `main`), which `dsh-tui` composes to approval policy never: every ask is rejected, so only read-only asks and reviews run. No order tool or broker connector. Defects (re-check): a token budget of 0 blocks every task run; foreground task runs are charged twice; `codex_task run` resumes the folder's last thread, not the task's; `displayReason` has the wrong type; a review's header prints "resumed undefined" (real series). Upstream publishes no outcome evidence; its 55 unit tests never start Codex.

## Method

- Fixed before the runs: [0009-real-prereg.txt](0009-real-prereg.txt), sha256 `268aa64e…a35371`, written 09:05:50 ET; the first run started 09:05:57 ET. Both times come from the owner's machine and cannot be proved from the repository. The published file is byte-identical to the one that ran (home paths were already written `~`). The arm key was drawn at 08:52:41 ET; four checks with other prompts ran on the same profiles before the file (listed in it). The rule is older: the assessment's (2026-11-12 21:34 ET), changed by the re-check (01:47:09 ET), which dropped the write-path condition and widened the last clause; amended after the always-on probes and after ADR 0007's Codex-only R4 runs of the same brief, before any run of this ADR's arms: (a) the with row sets `workspaceDir: ''` and `extraArgs: ['--disable', 'hooks']`; (b) the last clause counts only changes the with arm shows and the without arm does not, exempting under `~/.codex` only Codex's own session files, state databases and caches (narrowed after ADR 0007's runs changed `~/.codex/config.toml`); (c) the 5-run extension decides at the same fractions. R4's brief and rubric were hashed at 02:03:37 ET ([record](0009-prereg.txt)), 34 s after ADR 0007's first Codex run of the same brief had finished; the rubric's examples of real findings resemble that run's, so its independence from Codex's answer rests on timing alone.
- **Rule: adopt only if the with arm reports the `[DEFAULT]`-inheritance defect in at least 2 of 3 runs and the without arm in at most 1; with has at most one more false finding than without; the reference arm reports it in at most 1 of 3 or has more false findings than with; the always-on delta is at most 2,500 provider tokens; and nothing changes outside the plugin's state directory.**
- Arms: dsh 0.2.2-rc.1 with `deepseek-flash`, thinking on, effort max, `--permission-mode read-only --approval-policy never`, 1,800 s and at most 4 goal rounds; profiles `ab-0009-a` and `ab-0009-b` from the headless template, which differ only in the plugin's row (`stateDir` per run, `codexHome`, amendment (a)). The owner allowed temporary `ab-` profiles under the DeepSeek Harness home for these runs; dsh loaded its own key and no agent read it. Reference: `codex exec -s read-only --disable hooks`, `gpt-6-astra`, effort high. Order a1 b1 b2 a2 a3 b3, then c1 to c3. Each run in a fresh tree built from the base `96e82e6` alone, inside a mount namespace that hid `/mnt` (except the resolver file), `/run/WSL`, `~/src` (the main checkout, worktrees, other runs, the grading clone), `~/Jts`, `~/.ssh`, `~/.gnupg`, `~/.claude`, `~/.gemini`, `~/.config/gh` and `~/.npmrc`, with a scratch `HOME` and `~/.codex/config.toml` read-only; the network and the rest of the home, the dsh home and its key file included, stayed readable ([ab-dsh.md](ab-dsh.md)). Before every run a guard checked that nothing listened on the paper Gateway's port and that no Gateway process ran; it said down before all 13 starts. This ADR's first attempt at R4 was stopped at 02:04 ET before its reference arm's first run by the first round's guard, which matched command lines (no Gateway was up).
- Graded by the measuring agent, not blind, from each final answer against `39cb68e` with the rubric, six conventions fixed in the pre-registration and a [grading aid](0009_real_grade_aid.py). A void run is one whose result is not counted for its arm because a stated rule was broken; a void in the arm with the addition counts against it. Rule 9(a): a run that reads `39cb68e` or later history or the fix by another route, the network included, is void.

## Results

- Every one of the nine final answers reported the defect, and none held a false finding. But 4 of the 6 dsh runs are void under 9(a), 2 in each arm (a2, a3, b1, b2): the models read `.git/config` and `FETCH_HEAD`, then fetched the public repository's later history, the fix's patch included (57 distinct unauthenticated GitHub calls by the audit's count). In b1 and b2 the model had probed the defect itself before reading the fix; in a3 it first named it after. Counted: without 1 (a1, passed, 9 real findings), with 1 of 3 (b3, passed, 7), reference 3 of 3 (5, 6 and 6 real findings, median 94.8 s). The extension rule did not apply.
- The rule, clause by clause: with at least 2 of 3, not met (1 of 3); without at most 1 of 3, one counted run, which reported the defect (3 of 3 on the answers alone); false findings, met (0 against 0); reference, not met (3 of 3, 0 false findings); always-on, not met (+2,547 against 2,500); last clause, failed by every run of every arm as written (dsh writes outside the plugin's folder), met as amendment (b) reads it. **The void rule, not the addition, decides the first clause**: both arms showed the same behaviour, and only the with arm's voids count.
- The plugin acted in one run: b3 made one `codex_review` call, after the dsh agent had found the defect; its Codex child (read-only, through dsh's subprocess service, 253,145 Codex tokens, 109 s) added a listener-identity finding that reached the final answer. In b1 and b2 no tool of the plugin was called. The audit found that b3's Codex child called the lane's entry point `ibkr_paper.main(['restart'])` in-process with its settings read, port check, contract, account probe and engine patched; nothing connected to a Gateway port, but on a strict reading of the containment rule b3 would be void and the with arm 0 of 3. The result is the same.
- Cost: 8,188,240 DeepSeek tokens billed, about 92 % cache reads (runs: without 1,525,428, 1,456,126, 1,485,481; with 1,307,492, 1,431,451, 948,435; two checks 33,827); 964,706 Codex tokens (reference 681,130, b3's child 253,145, checks 30,431); 0 GitHub REST calls by the measurer.
- Containment: every checkout unchanged; no new name in the home directory; gitleaks 0 findings in 13 run folders; no tool call named the dsh home, an environment file, `.ssh` or `.codex`, though the key file stayed readable to the shell; three runs listed `~/Jts`, which was the empty scratch home; `~/.codex/config.toml` kept its sha256, being read-only, so the series cannot show what an unprotected child would do; 7 Codex threads remain in the owner's `~/.codex`; the owner's `dsh-tui` profile file was rewritten with unchanged content during the series by a process not identified. Hiding `/mnt` ends name resolution in this distro (`/etc/resolv.conf` links into `/mnt/wsl`); the resolver file was shown read-only. Raw runs stay on the owner's machine.

## Decision

Not adopted, by the rule fixed before the runs: the with arm reached 1 of 3 counted runs, Codex alone found the defect in 3 of 3 with no false finding, and the always-on cost is 2,547 DeepSeek tokens on every request against a ceiling of 2,500. The defect was reported in every answer of every arm, and the first clause fails on the void rule, not on the plugin. The series shows little about the plugin itself: R4 is a task the arm without it and Codex alone already solve, and it was called once, after the defect was found. R4 is a review, which `AGENTS.md` does not give DeepSeek Harness. A further dsh series on a public base needs a network bound for the shell tool or a private base (ab-dsh.md), and a task Codex alone misses. Nothing changes: no profile, `setup.sh` or `check_dsh` line.
