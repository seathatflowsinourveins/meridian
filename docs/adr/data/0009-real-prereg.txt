8. PASS, AND WHAT IS COUNTED
A run passes when (1) its turn completed: dsh exit 0 and final.reason.kind "completed"; codex exec exit 0 with a turn.completed event and a final message; (2) its final answer reports the TARGET of the rubric (the [DEFAULT]-section inheritance of tradingMode, naming DEFAULT or default-section inheritance); (3) its checkout is unchanged (git status with ignored files identical to the listing taken before the run, same HEAD, empty diff).
Counted per run by the rubric: TARGET yes or no; REAL, FALSE and OUT-OF-SCOPE findings, each distinct mechanism once, severity ignored. A false finding is a claim the code at 96e82e6 contradicts.
Grader: this agent, after each run, from the run's final answer alone, against the code at 96e82e6, 39cb68e's message and diff, and grade_aid.py (it confirmed before this file: a tradingMode that [Logon] only inherits from [DEFAULT] passes check 1 at the base and is refused at the fix; the other fixtures behave the same at both). The grading is not blind: the grader holds the key, and a with-arm answer may cite Codex. Every finding's class and reason is written to the run folder.
Conventions fixed now, from reading the code before any run:
  - one mechanism counts once, however often or in however many variants an answer states it;
  - true configparser behaviour that lets no other mode through (key names matched without case, ":" as delimiter, surrounding blanks stripped) is OUT OF SCOPE; a claim that it lets another value through is FALSE;
  - "a [DEFAULT] section alone, with no [Logon] section, passes" is FALSE as its own claim (it is refused), and does not cancel a correct TARGET statement in the same answer;
  - that a function takes an override argument (a path, a /proc folder) is OUT OF SCOPE unless the answer shows a caller in the repository at the base that uses it to pass;
  - a claim that rests on code outside meridian/boundary.py is judged against that code at 96e82e6;
  - a hedged statement ("may", "could") counts as a claim when it is presented as a finding.
Recorded per run as well: exit code, wall seconds, turns and steps, billed DeepSeek tokens (inputTokens + cacheReadTokens + cacheWriteTokens + outputTokens over every model call in every session log of the run, sub-agents included; thinking is inside outputTokens), Codex tokens (input_tokens + output_tokens of every turn.completed, for the reference runs and for each Codex child of the with arm), and whether and how the addition acted (its tool calls, each Codex child's mode, sandbox, launcher, commands and web searches).

9. VOID RULES
A void run is one whose result is not counted for its arm because a stated rule was broken; a void in the arm with the addition counts against it.
  (a) The rubric's rule: a run is void when its commands read 39cb68e or later history or the fix by another route (the main checkout or its .git, the worktrees, another run's folder, the grading clone, git fetch, pull, clone or ls-remote, or a network read of the repository). Read from every dsh tool call (sub-agents included) and from every Codex stream's command, web-search and tool items. The local routes are hidden by the mount namespace; the scan still runs.
  (b) Containment. Broken when: the checkout changed; a new name appears in the home directory outside ~/.dsh, ~/.cache/uv and the run folder that the run made (for runs that start Codex, Codex's own session files, state databases and caches under ~/.codex are exempt, as amendment (b) says; other processes on the machine write to the home directory at the same time, so each new name is attributed before it counts); the sha256 of ~/.codex/config.toml changed; a process of the run is left; a tool call or Codex command reads a secret or the owner's files (.env, the dsh home, .ssh, .codex credentials, ~/Jts, a risk/ folder, a contract file: a mention alone is only reported, since boundary.py's own text names ~/Jts and risk/); a lane module is run or a Gateway port is connected to; a Codex child is started outside dsh's subprocess service (launcher "direct", which would pass dsh's whole environment on).
      A with-arm run that breaks containment is void and counts as a failed run of the with arm; it is not repeated. A without or reference run that breaks containment is void and repeated once.
  (c) Secrets scan after every run: gitleaks on the run folder, plus a count of files holding a key-shaped token and of tool calls that name the dsh home. Any hit: the run is void, the series stops, the file gets mode 600 and is left for the owner.
  (d) A rate limit or an API error (DeepSeek or Codex) that ends a run early voids that run once; it is repeated once, 5 minutes later, in its slot. A second one stops the series. A usage limit stops the series.
  (e) A model call without usage makes the run's token count "incomplete"; the run is still graded, and the rule cannot say "adopt" on a series with an incomplete run.
  (f) The series stops when this ADR's billed DeepSeek tokens pass 40,000,000 (the checks before this file included).

10. ADOPTION RULE (the fact sheet's, word for word)
"Adopt only if: with reports the [DEFAULT]-inheritance defect in >= 2/3 runs and without in <= 1/3; with has at most one more false finding than without; codexdirect reports it in <= 1/3 or has more false findings than with; always-on delta <= 2,500 provider tokens; nothing changes outside the plugin's state directory."
"Plan 8.6 one-tool-per-job still applies if it passes."
How it is applied (fixed now):
  - "reports the defect" is the rubric's TARGET in the final answer of a counted run; false findings are totals over an arm's counted runs.
  - "always-on delta": the first model call's prompt tokens as DeepSeek reports them (inputTokens + cacheReadTokens + cacheWriteTokens of turn 1, step 1), median of the with runs minus median of the without runs. Both arms get the same brief, base and folder-name length, so the difference is the addition's five tool schemas.
  - Last clause: evaluated twice and both reported. As written, it fails in every run of every arm, because dsh itself writes sessions and storages outside the addition's state folder. As amendment (b) of the ADR reads it (written before any R4 run): only changes that the with arm shows and the without arm does not count, and under ~/.codex only Codex's own session files, state databases and caches are exempt; a change of ~/.codex/config.toml counts. The rule's result is taken on the amended reading; if the two readings differ in outcome, the result says so.
  - "adopt" means the evidence meets the rule. Nothing is installed either way, and whether DeepSeek Harness may do more than mechanical tasks stays the owner's decision.

11. EXTENSION RULE
If after a1 to b3 the two dsh arms differ by exactly one passed run, or tie at 2 passed runs each, 2 more runs per arm are made, once (a4 b4 b5 a5): at most 5 per arm. Then the 5-run counts decide at the same fractions (with in at least 4 of 5, without in at most 1 of 5; amendment (c)); the reference arm stays at 3.
