# ADR 0010: dsh-gungnir goal verification for DeepSeek Harness (plan 8.6)

**Status: not adopted, 2026-11-13.** Decided on the source at the pin, two live install probes (the re-check's and the measurement's) and a capture of dsh's first request without it; no with/without run was possible (see Results). Assessed 2026-11-12; an independent re-check on 2026-11-13 ran 63 checks (57 confirmed, 5 corrected, 1 unverifiable, 0 refuted) and agreed with the verdict; its corrections, and the real findings of later reviews of this text (their upstream and raw-capture reads are in the results), are applied here. Data: the [results](0010-results.json), the baseline's [always-on split](0010-always-on.json), the [pre-registration](0010-prereg.txt), the [arm key](0010-key.txt), the [overlay](0010-overlay.cordis.yml) and the scripts as they ran ([capture stub](0010_capture_server.py), [splitter](0010_split_request.py), [session-log reader](0010_dsh_session_log.py), [token counter](0010_count_tokens.py), [text rebuild](0010_reconstruct.py)); the shared method is [ab-dsh.md](ab-dsh.md) with task R2 of [ab-tasks.md](ab-tasks.md).

## Need

A DeepSeek Harness (dsh) agent can mark a goal complete while the work still fails: a false "done". dsh 0.2.2-rc.1's base bundle already composes `goal`, `goal-round-driver`, `/goal` and the `update_goal` tool: its system paragraph on goals, in every request, says to mark a goal complete only when the objective is achieved, and each goal round's prompt asks for evidence first (`goal-round-driver/src/prompt.ts` L18-L23). Neither runs a check; the handbook's Goals section (`docs/HANDBOOK.md` on branch `m2/handbook-size-budget`, not yet on `main`), noting that no runtime here runs one of its own, has every goal name a command whose exit code decides and whose output the session prints. The candidate claims to add that check, of exit codes and files, when the model claims completion. Outside the agent, the lead's exit-code grading and CI (ruff, pyright, pytest) already decide whether work is done. Inside `dsh-tui`, Orca mounts `@deepseek-ai/dsh-hooks-claude-code` for its status hooks (`UPSTREAM.md`), which runs Stop hooks at each turn stop (ADR 0012); Orca's hook configuration was not read, so whether a command hook on that seam already does this job is not known. Each of these covers the job in part; none is a check the dsh agent runs on itself.

## What it installs, writes and sends

Read in the source at the pin and in both npm tarballs; nothing was installed (see Results).
- A bundle row `gungnir` (`maxGoalRounds` 64) and in-process handlers on `tools/result`, `agent/pre-step`, `agent/turn-stopping`, `agent/created`, `goal/changed` and `gungnir-loop/*`, plus a service `gungnirAdaptive`. Commands `/ultragoal` and `/gungnir`, UI only (dsh: commands add no model tokens). Model tools: none in the default mode `passive='bpar'`, 1 in `'s1+s2'`, 3 in `'off'`. No system-prompt text, MCP server, LSP, network code, `child_process` or install script.
- At `update_goal(complete)` it runs each `/ultragoal --spec` exit-code command through the `run` method of dsh's shell executor, which dsh 0.1.2-rc.1 had and 0.2.2-rc.1 to rc.3 lack, so on the stack none starts (Results). Where one did start, it would run unsandboxed: the Orca unit sets `DSH_PERMISSION_MODE=danger-full-access` (`deploy/wsl/setup.sh` line 92 on `main`). Its LLM rubric check (L4) is unreachable: a spec that uses one is rejected.
- Writes `gungnir_ledger.json` (specs with their commands, interventions) under the profile's storage-json root (`$DSH_HOME/storages` by default), which removal leaves behind. At start it reads, then deletes, `<parent of cwd>/p2-supply-<dir>.json` if one exists (a parse failure stops the plugin). Mode `'p1'` writes probe scripts to the temp folder. An install adds it to the profile's `package.json`, lockfile and `node_modules` (`dsh-gungnir`, `gungnir-core`, `yaml`, `zod`); an exemption would add the profile's `compatibility.json`.

## Results

- Gate 0 failed, live, on 2026-11-13 at 01:56 ET, as in the re-check's earlier probe: exit 1, "installation rejected: Plugin dsh-gungnir@0.2.1 is incompatible with dsh 0.2.2-rc.1", "nothing was installed". dsh-gungnir pins its 10 `@deepseek-ai/dsh-*` peers to exactly `0.1.2-rc.1`, and dsh requires every such peer to match its own version (`app-boot/src/plugin-compatibility.ts` L51-L74); startup would skip the bundle too. The owner's `~/.dsh` was unchanged (hashes and listings before and after).
- Smoke: not run (needs the install, which Gate 0 refused, and `/ultragoal`, which headless cannot issue).
- Always-on: without arm 5,812, 5,812 and 5,812 tokens (median 5,812; the three differed by one character of the working folder; each probe ended with dsh exit 1 on the stub's 401). With arm: no run, so no measured delta (0 from the source).
- R2: 0 runs in either arm, so no medians, delta, pass counts per arm, voids or Codex delegation to report, and the rule is undecided (Method); the measurement's record gives its result as "not adopted", which is Gate 0's outcome, not the rule's. The with arm cannot be installed. Spec mode also needs `/ultragoal`, a slash command dsh headless cannot issue (no command adapter); the default mode needs none, since its check fires on any `update_goal(complete)` and headless offers `create_goal` and `update_goal`. dsh lets the model create a goal from a direct human request in a top-level turn, which R2's brief is, but `create_goal`'s description says "not for single-turn work", so on R2, small single-turn work, the model would probably not open one (untested; the model's call). A without arm alone is not an A/B, so the DeepSeek Harness real-task runs of 2026-11-13 did not include this ADR. No model call was made: 0 DeepSeek tokens billed.
- No machine policy blocked it: `/etc/claude-code/managed-mcp.json` and `/etc/codex/requirements.toml` do not govern dsh, and the plugin adds no MCP server. The block is dsh's own version check. An exact-version exemption (which dsh warns may cause crashes or data loss) would not make the check work: it calls `ctx.shell.run`, and dsh's shell executor has only `resolve` and `execute` in 0.2.2-rc.1, rc.2 (`ddac967`), rc.3 (`38a6a5c`) and `master` (`39163dd`), each read 2026-11-13 (results), so every exit-code check would report exit -1.
- Without a spec (the default) little is left: a successful `update_goal(complete)` clears the tool-error state before the check runs; dsh's bash reports a non-zero exit as `[exit code: N]` text, not as an error; pytest prints none of its test-run markers (substring tests, so other output can match by accident). The check runs after `update_goal(complete)` has succeeded and only injects a message: it is not a gate. Its stall nudge also fires after 8 model steps with no tool result, plain question-and-answer turns included.
- Upstream's own evidence (P2 stage report at the pin): author-run, 50 valid rows of 54, n=2 per cell, Node fixtures, dsh 0.1.2-rc.1. False completion caught: E2 2/2 (from the benchmark's hidden contract, not from exit-code checks), E3, nearest the shipped default, 1/2 with both runs still failing, E0 (native) 0/2. Its pre-registered cost gate G1 failed on its zero-tolerance criteria: +1.5 median round trips (E0 12 against E2 13.5) and one healthy-path intervention (a correct catch of a malformed `update_goal` call); the token rise, +7.8 % (median 24,151.5 against 26,025), was within its +10 % limit. A v0.1 fix then passed on 3 runs and 3 replays. The npm README still shows 0 extra round trips; only the repository README was corrected (+1.5), on 2026-10-27.
- Containment: the measurement's notes record that before the install probe, before each probe and at the end a guard checked that nothing listened on the paper Gateway's port and that no Gateway process ran; its commands and output were not kept and no guard script is published, so that sentence is the only record. The main checkout was not touched; package caches went into the evidence folder. The aggregates are in the data files above.

## Decision

Not adopted, on Gate 0 and the source, not on the outcome rule, which with no runs is undecided. Gate 0 only says to stop; the step from its failure to not adopted, rather than deferred, is a judgment made after the probe, on facts no run would change: dsh refuses the install, and Gate 0 says to stop there; with an exemption the candidate's exit-code check still cannot run on 0.2.2-rc.1 to rc.3 (no `ctx.shell.run`); its default mode catches almost nothing on this Python repository; and its evidence is small, self-run, Node-only and on dsh 0.1.2-rc.1. Zero always-on cost does not change that, and no overlap decides it: the overlaps are partial. Exit codes are already checked outside the agent, by the lead's grading and CI; whether a command hook on Orca's Stop-hook seam in `dsh-tui` already does the job inside it is not known (Need). Inside dsh, the goal tools and system paragraph (440 tokens of every request measured here) say to complete only when achieved, each goal round's prompt asks for evidence, `bash` tells the model to check every `[exit code: N]` marker, and `repeat-tool-reminder` (thresholds 3, 5, 8; identical calls only) nudges loops; none runs a check. Claude Code's and Codex's `/goal` are judged by a model, not by a command (the handbook's Goals section). Nothing changes: no profile, `setup.sh` or `agents-check` line. A measurement needs a release that declares 0.2.x dsh peers (or `engines.dsh`), calls the executor's `execute` and passes the smoke spec with no exemption, and, for spec mode, a non-UI way to start `/ultragoal`.
